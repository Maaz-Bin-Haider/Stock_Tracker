  The document turns the spec into a build plan. The decisions that shape everything:

  The stock ledger design (section 5) is the heart. The ledger is an append-only table — rows are never
  updated or deleted; corrections and refunds are reversal rows referencing the original. Balances live in
  a materialized stock_balances table (product × location × bucket) updated in the same database
  transaction as each ledger insert with row-level locking, so list pages and the dashboard are fast while
  the ledger stays the source of truth. A rebuild_stock_balances command recomputes everything from the
  ledger and reports drift, which also doubles as a consistency check in tests. Critically, there's
  exactly one writer: a post_event service in the inventory app that every module must call — it enforces
  transactions, quantity validation, the negative-stock confirmation flag, and in-transaction audit writes
  in one place, so a future feature can't forget any of them. Section 5.2 has the full event→ledger
  mapping table (purchase = +PENDING, collection = −PENDING/+PHYSICAL, shipment = −PHYSICAL/+IN_TRANSIT,
  etc.) which also serves as the test specification.

  Backend: one Django project, 11 focused apps (core, accounts, masterdata, products, purchases,
  shipments, sales, inventory, reports, audits, attachments). Statuses and pending quantities are always
  computed, never stored as user input. Money values (AED conversion, GST) are frozen at entry time so
  history never drifts when rates change.

  API and auth: DRF under /api/v1/, with stock-changing actions as explicit endpoints (collections,
  refunds, receipts) rather than generic updates. Session-cookie auth behind a single nginx origin —
  simplest correct option for a first-party web app, and login/logout audit comes free. Permissions are
  one class per module driven by a static role matrix mirroring the spec. The OpenAPI schema generates the
  frontend's typed client so the two sides can't silently drift.
